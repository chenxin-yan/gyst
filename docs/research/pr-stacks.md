# #68 — Stack models and review context

_Checked 2026-09-25; primary documentation, source, live APIs, and read-only local inspection._

## Summary

- **GitHub now has native stacks**, in public preview: explicit membership, ordered layers, navigation, REST/GraphQL support—not merely conventional PR base chains ([docs](https://docs.github.com/en/pull-requests/get-started/about-stacked-prs)).
- This user demonstrably uses **GitHub stacks and agent-assisted restacking**. Local `gh-stack` metadata is historical/stale; Graphite usage is not established. Their `gt` checkout is **General Translation**, not Graphite (evidence below).
- Stack topology and review diff boundaries are separate: branch chains, synthetic bases, and overlapping PRs require different interpretations (comparison below).
- **Recommendation:** accept explicit, immutable layer ranges from the harness first; add GitHub-native discovery before proprietary metadata adapters. Keep stack editing and agent execution outside gyst.

## Recommendation and trade-offs

**Proposed minimal contract:** each layer supplies stable ID, title, parent-layer ID, optional PR URL, immutable base/head OIDs, range semantics and provenance. Keep stack membership separate from diff endpoints. Validate objects and reject cycles/ambiguous boundaries; don't silently use trunk for every layer.

Show a compact ordered selector, current position, parent context, and per-layer walkthrough/groups/threads. Pin comments to layer **and snapshot**; restacking creates a new snapshot rather than silently moving anchors. Keep cumulative stack diff optional and labelled.

Start with harness-supplied ranges and ordinary Git; add read-only native GitHub discovery for this user's demonstrated workflow. This avoids eight adapters and cloud authentication in the first version, at the cost of harness-supplied metadata. Branch-base-chain inference is a labelled fallback, not authoritative membership. No restacking, merging, graph editor, or agent spawning belongs in this increment.

## Open questions / residual risks

- Should v1 accept explicit layers only, or must it discover native GitHub stacks automatically?
- Is historical `gh stack` still the preferred workflow, or are agents now managing branches/API stacks directly?
- Should sibling stacks and uncommitted layers be selectable initially, or explicitly unsupported?
- Preview APIs and private metadata can change; local state is demonstrably stale. Graphite's exact current storage format remains unverified; sampled sessions cannot prove non-use of other tools. Rewritten or missing Git objects need an explicit unavailable/stale state, not invented ranges.
