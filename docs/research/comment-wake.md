# Research: waking a harness agent for gyst comments (#63)

## Summary
- **Recommend v1: human-triggered, one-shot “respond to review” skill/prompt.** On submission, gyst stores comments and offers a copyable instruction (or a harness-specific command); the human sends it to the *already open* coding-agent conversation. The agent fetches pending comments, answers by stable comment ID, then exits. This is a proposed design, not an existing gyst feature.
- A blocking `gyst ... wait` ties up a tool turn and inherits harness timeouts; it is not portable as an indefinite wake-up. A short, explicitly bounded wait is possible only while a turn is active.
- Native automatic wake is possible in some installations—Pi extensions and Claude Code Monitor—but adds harness-specific setup, live-session dependence, and, for Claude, bounded monitor lifetime. No universal automatic wake mechanism is documented for these four harnesses.
- MCP notifications and elicitation are **not** a portable way to inject an unsolicited user turn into an idle coding agent; MCP is useful for fetching/posting review data **after** a human or harness has resumed the turn.

## Findings

1. **Human invocation (direct evidence).** Pi 0.87.1 advertises skills and permits explicit `/skill:name` invocation even if the model would not select a skill on its own ([local Pi skills.md, lines 42–57](/nix/store/q9gk8vgqbcs39yd3q0a8y48rdz53rmbw-pi-coding-agent-0.87.1/lib/node_modules/pi-monorepo/docs/skills.md)); Claude Code supports skills as slash commands ([Claude skills](https://code.claude.com/docs/en/skills)); Codex supports skill workflows ([Codex skills](https://developers.openai.com/codex/skills)); OpenCode supports [custom commands](https://opencode.ai/docs/commands/) and [skills](https://opencode.ai/docs/skills/). **Interpretation:** a plain-language prompt that names the pending review is the smallest cross-harness baseline; a packaged skill improves repeatability but does not itself wake an idle agent. **Confidence: high.** UX cost: one human switch/send; failure: wrong conversation, closed session, omitted invocation, stale or duplicate comments.

2. **Blocking wait (direct evidence, plus inference).** Claude Code’s Bash default command timeout is 120 seconds and its model-selectable maximum defaults to 600 seconds ([environment variables](https://code.claude.com/docs/en/env-vars)); command hooks have separate timeouts ([hooks](https://code.claude.com/docs/en/hooks)). Pi’s loop only makes another model request when tool results or queued messages require one ([local Pi how-pi-works.md, lines 5–22](/nix/store/q9gk8vgqbcs39yd3q0a8y48rdz53rmbw-pi-coding-agent-0.87.1/lib/node_modules/pi-monorepo/docs/how-pi-works.md)). Codex tool guidance documents command-specific `timeout_ms` and interactive `exec_command`/`write_stdin` sessions ([OpenAI model/tool guidance](https://developers.openai.com/api/docs/guides/latest-model?model=gpt-5.3-codex)); OpenCode exposes shell calls and async prompts, not an advertised indefinite shell wait ([OpenCode server](https://opencode.ai/docs/server/)). **Inference:** an unbounded foreground wait risks a canceled tool, hung agent, costs and session/terminal closure; an idle agent cannot voluntarily call a tool until prompted. Exact stock Pi, Codex CLI, and OpenCode shell ceilings were **not verified**, so do not hard-code a portable number. **Confidence: high** for Claude’s documented limit, **medium** for cross-harness inference.

3. **Native background/monitoring (direct evidence).** Pi extensions can start session-scoped watchers on `session_start`, clean up on `session_shutdown`, and submit a user message with `pi.sendUserMessage()` ([local Pi extensions.md, lines 56–78](/nix/store/q9gk8vgqbcs39yd3q0a8y48rdz53rmbw-pi-coding-agent-0.87.1/lib/node_modules/pi-monorepo/docs/extensions.md)). Third-party [pi-processes](https://github.com/aliou/pi-processes/blob/main/README.md) documents log/output watches that wake Pi; [pi-subagents’ bundled intercom](https://github.com/fitchmultz/pi-subagents/blob/main/docs/intercom.md) documents steering an idle connected Pi session, but requires its broker/extension and is **not** core Pi or a gyst integration. Claude Code [background Bash](https://code.claude.com/docs/en/env-vars) allows long-lived subprocesses; [Monitor](https://code.claude.com/docs/en/tools-reference#monitor-tool) actually feeds lines/events back to Claude and can interject while the session continues (default deadline 5 minutes, maximum 30; `-p` maximum 10). A Monitor **WebSocket** to gyst’s loopback daemon is specifically blocked: Claude rejects private/link-local destinations; a monitored shell command polling gyst is the alternative. [Plugin monitors](https://code.claude.com/docs/en/plugins/components#monitors) run automatically but only in eligible interactive sessions, not `-p`; availability is additionally limited by provider/telemetry settings ([Monitor](https://code.claude.com/docs/en/tools-reference#monitor-tool)). Claude [Notification/Stop hooks](https://code.claude.com/docs/en/hooks) react to Claude lifecycle events, not gyst’s arbitrary browser comment event. **Interpretation:** automation is feasible per harness but carries installation, permissions, restart, expiry, and duplicate-delivery costs. **Confidence: high.**

4. **Codex/OpenCode native features (direct evidence, limits).** Codex’s [`notify`](https://developers.openai.com/codex/config-advanced) runs an external command on supported events currently only `agent-turn-complete`; [hooks](https://developers.openai.com/codex/hooks) run during configured lifecycle events and can be async. Neither document promises arbitrary external-event injection into an idle CLI turn. OpenCode [plugins](https://opencode.ai/docs/plugins/) subscribe to events such as `session.idle`; its [server](https://opencode.ai/docs/server/) exposes `POST /session/:id/prompt_async` (returns 204), which an installed, user-authorized client could use to submit a new message to an existing session. **Interpretation:** OpenCode offers a possible harness-owned bridge; Codex completion alerts are not a gyst-comment listener. Both require extra integration/permission; absent a live session, no automatic reply. **Confidence: medium** (no end-to-end gyst bridge verified).

5. **MCP (direct evidence and interpretation).** MCP tools are invoked by clients; `listChanged` advertises *changes in the tool list*, not new review content ([MCP tools, 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). Elicitation asks the client to collect **user information** during an interaction ([MCP elicitation](https://modelcontextprotocol.io/specification/2025-11-25/client/elicitation)); sampling is a server-requested nested generation where the client controls model access ([MCP sampling](https://modelcontextprotocol.io/specification/2025-11-25/client/sampling)). The protocol says implementations choose their own UI behavior ([MCP tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)). **Interpretation:** no specified cross-harness mapping from server notification/elicitation to “start a new user turn in the existing CLI conversation”; sampling would also shift orchestration toward gyst, contrary to scope. **Confidence: high** for protocol semantics, **medium** for individual client behavior (not exhaustively tested).

## Comparison

| Mechanism | Today in pi / Claude / Codex / OpenCode | Turn/timeout and UX | Principal failure |
|---|---|---|---|
| Human prompt/skill | All four; commands differ ([Pi skills](/nix/store/q9gk8vgqbcs39yd3q0a8y48rdz53rmbw-pi-coding-agent-0.87.1/lib/node_modules/pi-monorepo/docs/skills.md), [Claude](https://code.claude.com/docs/en/skills), [Codex](https://developers.openai.com/codex/skills), [OpenCode](https://opencode.ai/docs/commands/)) | New user turn, no idle tool timer; manual send | Human forgets/wrong agent |
| Foreground `gyst wait` | Shell available; no portable indefinite contract ([Claude env](https://code.claude.com/docs/en/env-vars)) | Occupies current tool turn; Claude 2m default/10m max | Timeout, cancellation, closed session |
| Native watcher/wake | Pi extension/third party; Claude Monitor/plugin; OpenCode plugin/API; Codex hooks only on lifecycle events ([Pi](https://github.com/aliou/pi-processes/blob/main/README.md), [Claude](https://code.claude.com/docs/en/tools-reference#monitor-tool), [OpenCode](https://opencode.ai/docs/server/), [Codex](https://developers.openai.com/codex/hooks)) | Automatic where supported; setup and version-dependent limits | Watch expires; plugin disconnected; duplicate wake |
| MCP notification/elicitation | Protocol support differs by client ([MCP](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)) | No standard idle-turn start | Notification ignored/not model-visible |

## Recommendation and trade-offs

**V1 (researcher inference):** keep pending comments durably in gyst and show a prominent **Copy instruction / Respond in agent** affordance; let the human paste into their existing harness session. Agent instructions should fetch by review/run ID, reply to each unresolved stable comment ID, and mark replies complete idempotently; support a short `gyst comments list`/`gyst comments reply` flow rather than mandatory MCP or polling. Preserve the per-run token as a secret; do not put it in copyable text or logs. This trades immediate hands-free response for no daemon-managed agents, no forever tool calls, no per-harness wake integration, and clear human consent. Optional later: **user-installed** Pi/Claude watchers or OpenCode plugin if repeated manual wake becomes demonstrably painful; do not assume Codex offers equivalent idle wake.

## Contradictions

None in the kept source passages. Claude’s background Bash **is not the same as** Monitor’s event-driven agent interjection ([tools reference](https://code.claude.com/docs/en/tools-reference#monitor-tool)); treating them as interchangeable would be misleading. Codex `notify` is an *agent-turn-complete* outbound alert, not inbound comment delivery ([Codex configuration](https://developers.openai.com/codex/config-advanced)).

## Open questions / missing evidence

- Human decision: should the browser button **copy a prompt**, display harness-specific invocation instructions, or both? Is manual response latency acceptable for v1?
- Confirm exact installed versions/capabilities and shell-tool timeouts for Codex/OpenCode/Pi in target environments; no end-to-end live-session wake benchmark was run. Decide whether comments arriving during an agent response should queue for the next explicit invocation.
- If automatic wake is later required, who installs/trusts each extension, and what should happen after session close, expired run token, or interrupted watcher? Keep retries/idempotent replies explicit.
