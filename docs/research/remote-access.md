# Research: gyst browser access from a MacBook to remote Linux (#65)

## Summary

- **Recommendation:** Keep gyst bound to remote `127.0.0.1`, retain its per-run token and strict Host/Origin checks; document an SSH **local** tunnel as the default MacBook workflow. No LAN bind or network-discovery feature is needed.
- On the MacBook, `ssh -N -L 127.0.0.1:LOCAL_PORT:127.0.0.1:REMOTE_PORT user@remote` forwards the Mac's loopback port to remote loopback; browse `http://127.0.0.1:LOCAL_PORT/?token=...`. `LOCAL_PORT` may differ from `REMOTE_PORT`.
- Print a copyable, tokenised loopback URL on the remote terminal; do not rely on opening a browser there. Detect SSH (`SSH_CONNECTION`) as a usability hint, not an authentication or networking guarantee.
- Explicit binding to all interfaces would expand exposure and require a separate secure-access design (TLS and stronger access controls). Tailscale Serve or a trusted HTTPS reverse proxy can provide access without changing gyst's loopback bind, but introduces external hostname/Origin configuration and a broader audience.

## Findings

1. **SSH forwarding is the closest precedent.** OpenSSH `-L` forwards a client-side listening port over the encrypted channel to a host/port reached *from the remote side*, and an explicit `127.0.0.1:` bind limits its local listener; `-N` avoids running a remote command ([ssh(1), `-L` and `-N`](https://man.openbsd.org/ssh#L)). code-server explicitly recommends `ssh -N -L 8080:127.0.0.1:8080 user@host` and a browser at `http://127.0.0.1:8080` ([code-server SSH guide](https://coder.com/docs/code-server/guide#port-forwarding-via-ssh)); VS Code Remote-SSH forwards remote ports to a local `localhost` URL and may substitute a different available local port ([Remote-SSH forwarding](https://code.visualstudio.com/docs/remote/ssh#_forwarding-a-port-creating-ssh-tunnel)). **Support: direct evidence; confidence: high.** Inference: using the Mac's `127.0.0.1` URL means browser-generated Host and Origin refer to the *Mac-side* hostname/port, not the remote machine's name; ordinary TCP forwarding does not rewrite HTTP headers.

2. **Copyable token URL is established, but its secrecy matters.** Jupyter generates token auth by default, logs copy/paste `localhost` token URLs, and accepts token in a URL parameter or Authorization header; a subsequent visit establishes a browser cookie ([Jupyter security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html)). Jupyter's `custom_display_url` explicitly separates displayed URL from actual listener for proxy/container setups ([Jupyter config](https://jupyter-server.readthedocs.io/en/stable/other/full-config.html#serverapp-custom-display-url)). OWASP warns URL-carried session IDs may leak via logs, history, bookmarks or Referer ([OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-management-implementation)). **Support: direct evidence; confidence: high.** Inference: a startup URL can bootstrap gyst's per-run session, but avoid echoing tokens in request logs, use no-referrer behavior, and remove the token from the displayed address after exchange for a scoped session if the current design supports it; do not add a new session system solely for forwarding.

3. **Host checks and CORS/Origin are different controls.** Jupyter defaults `allow_remote_access=False`: nonlocal Host values get 403 specifically against DNS rebinding; configured `local_hostnames` are a narrower alternative to disabling the check ([Jupyter config](https://jupyter-server.readthedocs.io/en/stable/other/full-config.html#serverapp-allow-remote-access)). Vite defaults to `localhost` binding, permits `--host 0.0.0.0`, and warns `allowedHosts: true` enables rebinding-based source disclosure; it separately warns permissive `server.cors` enables cross-origin source access ([Vite host](https://vite.dev/config/server-options.html#server-host), [allowed hosts](https://vite.dev/config/server-options.html#server-allowedhosts), [CORS](https://vite.dev/config/server-options.html#server-cors)). **Support: direct evidence; confidence: high.** Inference: for SSH forwarding, validate Host against `127.0.0.1`/`localhost` (with the *local* port, which may differ); for mutating HTTP requests and WebSocket handshake, validate Origin against the actual browser-facing scheme + Host + port. Do **not** reject a safe localhost Origin just because its port differs from the server's remote listener. Do not solve a forwarded-host mismatch by allowing all Hosts or CORS origins; reject foreign Host even with a valid token.

4. **Network sharing is an explicit alternative, not the default.** OpenCode `web` starts on `127.0.0.1` with a random port and auto-opens the browser; `--hostname 0.0.0.0` advertises network access, and `OPENCODE_SERVER_PASSWORD` adds HTTP Basic auth. Its `serve` command also defaults to `127.0.0.1` and offers explicit `--cors` ([OpenCode web](https://opencode.ai/docs/web/), [serve](https://opencode.ai/docs/server/)). Tailscale Serve proxies a service at `http://127.0.0.1:3000` to tailnet devices with HTTPS and tailnet access rules; Funnel instead makes it public ([Tailscale Serve](https://tailscale.com/kb/1312/serve)). Jupyter documents `ip='*'` only in a separately secured public-server configuration with HTTPS/password and `open_browser=False` ([Jupyter public server](https://jupyter-server.readthedocs.io/en/latest/operators/public-server.html)). **Support: direct evidence; confidence: high.** Inference: do not copy OpenCode's opt-in wildcard binding as gyst's default; a bearer token on plaintext LAN HTTP is insufficient against on-path interception.

5. **SSH detection is a UX hint.** OpenSSH sets `SSH_CONNECTION` for SSH-run sessions and `SSH_TTY` only when a PTY is allocated ([OpenSSH `session.c`, `do_setup_env`](https://github.com/openssh/openssh-portable/blob/master/session.c)). Jupyter prints URLs even when a browser can also open, and its config permits disabling opening ([Jupyter security](https://jupyter-server.readthedocs.io/en/latest/operators/security.html), [config](https://jupyter-server.readthedocs.io/en/stable/other/full-config.html#serverapp-open-browser)). **Support: direct evidence for environment/precedent; recommendation is researcher inference; confidence: high.** Suppress browser launch when `SSH_CONNECTION` is set (also offer `--no-open`); always print the URL. `SSH_TTY` alone misses non-PTY remote commands; SSH detection cannot detect all containers, IDE terminals or port-forward readiness.

## Recommendation and trade-offs

Document two steps: run gyst on remote loopback and note its selected remote port/token; on Mac run `ssh -N -o ExitOnForwardFailure=yes -L 127.0.0.1:LOCAL_PORT:127.0.0.1:REMOTE_PORT user@remote`, then substitute `LOCAL_PORT` into gyst's printed URL. Preserve exact localhost/127.0.0.1 Host allowlist and same-origin checks, with no dependency on the *remote* port in the forwarded browser origin; check every privileged endpoint/upgrade and token independently. Print a remote-loopback URL, **not** a purported Mac URL when its local port is unknown. Explicitly describe optional external proxy/Serve setup as advanced: configure only the *exact* trusted external Host and Origin, retain token, and require HTTPS/access controls; do not trust arbitrary `X-Forwarded-Host` or turn off rebinding defense. SSH costs a second terminal and manual port mapping but needs no new gyst networking feature. Local processes/users who can read the terminal URL or access the tunnel remain in the trust boundary; a remote-LAN/public bind creates far more exposure ([ssh(1)](https://man.openbsd.org/ssh#L), [code-server security warning](https://coder.com/docs/code-server/guide), [OWASP URL risks](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-management-implementation)).

## Contradictions / caveats

VS Code's **Remote-SSH** forwards remote service ports to localhost ([Remote-SSH](https://code.visualstudio.com/docs/remote/ssh#_forwarding-a-port-creating-ssh-tunnel)); its separate Microsoft **dev tunnels** port-forwarding page says that feature currently forwards only local services and optionally exposes a public URL ([dev tunnels](https://code.visualstudio.com/docs/debugtest/port-forwarding)). Do not conflate these. code-server's SSH recipe suggests disabling its password behind SSH; that does **not** justify removing gyst's per-run token, because an additional token protects against local unintended access ([code-server](https://coder.com/docs/code-server/guide#port-forwarding-via-ssh)).
