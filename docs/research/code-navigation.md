# Research: Code navigation in gyst diffs and old/new files

## Summary
- **Recommendation:** start with explicit agent-authored, reviewable links anchored to snapshot side/path/range; do not promise universal click-any-symbol navigation. This matches a walkthrough product rather than building an IDE. **Researcher inference.**
- If demand emerges, add opt-in, clearly labeled **candidate** definition/reference search using tags or ctags over *both complete snapshots*. Search results and nearby comments can provide a limited hover. GitHub and Sourcegraph both ship search-based navigation alongside more precise approaches ([GitHub](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github#about-navigating-code-on-github), [Sourcegraph](https://sourcegraph.com/docs/code-navigation/search-based-code-navigation)).
- Full LSP yields language-specific definition/references/hover but requires server installation, process management and two consistent project views, not just a file overlay ([LSP initialize](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/general/initialize.md), [didOpen](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/textDocument/didOpen.md)). **Researcher inference:** defer until demand and a deliberately narrow language list justify it.
- SCIP/LSIF are plausible future *import* formats for precomputed, revision-scoped navigation in a hosted product, but generating their indexes is a separate per-language/build problem ([SCIP schema](https://github.com/scip-code/scip/blob/main/scip.proto), [LSIF overview](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_overviews/lsif/overview.md)).

## Findings
1. **LSP contract and revision trap.** `textDocument/definition`, `/references` (project-wide), and `/hover` take document positions and return locations or hover contents; availability is per-server capability ([definition](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/definition.md), [references](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/references.md), [hover](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/language/hover.md)). The client supplies workspace roots at initialization; `didOpen` replaces the contents of that *opened document*, not the server's entire project view ([initialize](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/general/initialize.md), [didOpen](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_specifications/lsp/3.17/textDocument/didOpen.md)). **Researcher inference:** handing an old file's text to a server rooted at today's checkout can silently mix old caller with new imports/definitions. For reliable old/new queries, use isolated full-project old and new trees and separate server sessions (Git supports detached worktrees at commits: [git-worktree](https://git-scm.com/docs/git-worktree)); an uncommitted new snapshot needs a materialized overlay/tree too. Map diff hunk coordinates to each corresponding *full-file* side; never query a stripped diff as a project file. Dependencies and generated files may still differ from historical state. **Support:** direct protocol evidence; snapshot consequences are inference. **Confidence:** high for protocol, medium for cross-server behavior.
2. **Running it is a product, not a widget.** Servers have distinct executable and setup requirements: the TypeScript LSP implementation documents installing both its server and TypeScript and starting with `--stdio` ([typescript-language-server](https://github.com/typescript-language-server/typescript-language-server/blob/master/README.md)). A browser cannot launch native tools: VS Code web extensions run in WebWorkers; its browser-adapted JSON/CSS/HTML servers are exceptions ([VS Code web extensions](https://code.visualstudio.com/api/extension-guides/web-extensions)). Monaco-languageclient connects Monaco to worker servers or external processes through WebSockets, but does not provision language servers ([project README](https://github.com/TypeFox/monaco-languageclient/blob/main/README.md)). **Researcher inference:** local gyst would have to discover/configure binaries, spawn/stop and bound servers, route LSP requests, convert URI/ranges, handle missing capabilities and snapshot isolation; WebSocket is optional if the daemon can proxy LSP through its existing HTTP API. Hosted without a checkout requires browser-compatible analyzers or server-side checkout/build infrastructure. **Support:** direct product/protocol evidence and marked inference. **Confidence:** high.
3. **Light indexes are meaningfully different.** Tree-sitter `tags.scm` queries extract named definitions, references, and optionally docstrings for languages with suitable grammar/query files ([Tree-sitter navigation](https://github.com/tree-sitter/tree-sitter/blob/master/docs/src/4-code-navigation.md)). GitHub automatically offers Tree-sitter navigation for its [listed languages](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github#about-navigating-code-on-github), but its documented matching searches repository definitions/references by name; its older first-party comparison showed same-name noise, with stack graphs yielding more precise Python resolution ([GitHub announcement](https://github.blog/news-insights/product-news/precise-code-navigation-python-code-navigation-pull-requests/)). GitHub's open-source [stack-graphs README](https://github.com/github/stack-graphs/blob/main/README.md) now explicitly says GitHub no longer supports/updates it; do not assume it is a maintained drop-in engine. Universal Ctags offers many build-dependent parsers (`--list-languages`), but its reference tags cover only limited language areas ([manual, TAG ENTRIES](https://docs.ctags.io/en/latest/man/ctags.1.html#tag-entries)); Sourcegraph's fallback uses ctags for symbols, text search for references and nearby comments for hover ([Search-based navigation](https://sourcegraph.com/docs/code-navigation/search-based-code-navigation)). **Researcher inference:** small name indexes are cheap to construct on either snapshot but cannot reliably distinguish shadowing, overloads, or unresolved imports. **Support:** direct evidence plus inference. **Confidence:** high.
4. **Precomputed semantic data.** SCIP stores per-document occurrence ranges/symbol IDs, definition roles, and optional documentation/signatures ([`scip.proto`](https://github.com/scip-code/scip/blob/main/scip.proto)); LSIF explicitly aims to answer definition/references/hover in a web UI without running an LSP server at query time ([LSIF overview](https://github.com/microsoft/language-server-protocol/blob/gh-pages/_overviews/lsif/overview.md)). Sourcegraph lists maintained precise indexers for Go, JS/TS, C/C++, Java/Kotlin/Scala, Rust, Python, Ruby, and C#/VB, and recommends CI indexing for complex builds ([precise navigation](https://sourcegraph.com/docs/code-navigation/precise-code-navigation)). Its auto-indexers *clone repositories* and select commits under policy; uploaded indexes are mapped to applicable commits ([auto-indexing](https://sourcegraph.com/docs/code-navigation/auto-indexing), [uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads)). **Researcher inference:** gyst could consume supplied indexes later without a local checkout on the *viewer*, provided the host retains old/new file content and side-specific indexes; generating an index for a dirty working tree still needs a buildable snapshot. Absent an exact index, do not claim exact historical matches. **Support:** direct evidence; applicability to gyst inferred. **Confidence:** medium-high.

## Comparison

| Option | Language reach / setup | Old/new accuracy | Runtime/build cost | Hosted, no local checkout? |
|---|---|---|---|---|
| Agent-authored links only | Any file the agent can inspect; no server/index; pointers must carry side/path/range and optional explanation | Human-authored/agent-authored, not comprehensive; can target exact frozen snapshots if validated | Lowest; agent review effort | Yes, if snapshot files and links are stored |
| Tree-sitter tags / ctags + name search | Grammar and tags-query availability / installed ctags parsers; indexing/lookup implementation | Correct-side text positions if both snapshots indexed; ambiguous semantic matches | Low to moderate, proportional to snapshot size | Yes, if hosted server has snapshot files or accepts prebuilt indexes |
| Stack graphs | Rules exist for fewer languages; author/maintain scope rules ([README](https://github.com/github/stack-graphs/blob/main/README.md)); upstream unsupported | Potentially better name resolution on frozen snapshot; not full type/build analysis | Moderate-high custom integration | Yes with snapshot files and hosted processing |
| Managed LSP | Per-server languages and toolchains; discovery/process/transport/workspace | Potentially best when separate complete old/new environments and dependencies exist; otherwise misleading | High, potentially two concurrent project analyzers | Only with hosted compute/checkouts or browser-compatible server |
| SCIP / LSIF import | Per-language indexer, usually CI/build; gyst builds consumer, not generator | Strong when index matches snapshot; stale/missing index needs explicit fallback | Expensive indexing; cheap-ish serving plus storage | Yes, once index and file contents are supplied |

Rows' relative costs and applicability to gyst are **researcher inferences** from the cited implementation requirements; they are not benchmarks.

## Recommendation and trade-offs
Ship **only agent-authored intra-snapshot links first**, visibly attributed as guidance, not precise semantic navigation. Resolve links to immutable `{side, path, range}` full-file targets; diff links translate to side-specific full-file positions. Reject missing files/ranges and external or malformed destinations at the trust boundary. **Researcher inference:** this preserves old/new correctness and hosted portability without making gyst responsible for tools, dependencies, or a cross-language index. Downside: sparse coverage, potentially wrong agent links, and no automatic hover/reference enumeration; the human should be able to inspect/correct them.

If usage shows people repeatedly need ad hoc exploration, pilot *opt-in candidate search* against both snapshots (existing text search first; tags only when it measurably improves results). Do not build stack-graph rules or server orchestration speculatively. If customers already produce SCIP/LSIF, import might precede LSP. Reconsider LSP only for explicitly chosen languages/projects with real demand and verified historical snapshot semantics.

## Contradictions / missing evidence
No direct contradiction: GitHub's tree-sitter support list does **not** mean all listed languages have semantic precision; its Python stack-graphs announcement is historical, while the public stack-graphs project now says unsupported ([GitHub docs](https://docs.github.com/en/repositories/working-with-files/using-files/navigating-code-on-github), [announcement](https://github.blog/news-insights/product-news/precise-code-navigation-python-code-navigation-pull-requests/), [repository](https://github.com/github/stack-graphs/blob/main/README.md)). No empirical latency, RAM, quality, or developer-demand measurements for gyst; relative costs are inferred. Automated `source_check` returned passages but no semantic verdict, so the decisive claims above were checked directly against the cited primary documents instead.

## Open questions for human decision
1. Does clickable **agent guidance** satisfy v1, or is arbitrary-symbol exploration a launch requirement?
2. Will gyst persist entire immutable old/new trees (including uncommitted state), or only changed files? Cross-file results require the former or an external index.
3. Would a future host be permitted to fetch/build private code, accept uploaded indexes, or neither?
